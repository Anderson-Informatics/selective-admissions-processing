# Validation "Check" Labels: Administrative Guide

These labels flag application details that need a person to review. A label is **not proof that an applicant made a mistake** and does not, by itself, determine eligibility. Open the application's validation issue to see the specific message and any related submission IDs before taking action. An application may have more than one label.

| Label | Why you may see it | What to check and do |
| --- | --- | --- |
| **Check Age** | The birth date is missing, cannot be read as a valid date, is in the future, gives an age outside **5-21**, or gives an age that is unusual for the listed grade (grades 6-12). | Compare the birth date and grade with the application and available records. Correct a data-entry or mapping error if confirmed. If the information is accurate, follow the team's usual process for reviewing an unusual age or grade; do not change a correct birth date just to clear the label. |
| **Check Student Number** | An applicant marked as **DPSCD** has no student number, a number containing something other than digits, or a number that is not **5 or 8 digits** long. | Confirm whether the applicant is a DPSCD student. If so, verify the number against the record in PowerSchool and correct it if needed. If the applicant is not a DPSCD student, leave field as 0. They may need to submit a new application to fill out the correct information in order to be able to upload their transcripts. |
| **Check Name** | The full-name field does not appear to contain the student's listed first and last names. It may contain a parent or guardian's name instead. | Compare the full name, student first and last names, and parent/guardian names. Confirm whose name belongs in each field before correcting it. Common suffix differences such as Jr. or III should not cause this label on their own. |
| **Check for Duplicate** | Two or more submissions have matching names and birth dates, based on either the full name or the separate first and last names. Submissions with matching names and missing or unreadable birth dates can also be flagged. | Open the other submission(s) listed in the issue. Confirm whether they are the same applicant or different people with matching details. Follow the team's duplicate-submission process; this may involve identifying the most correct application and withdrawing the other duplicate. |
| **Check Documents** | The application indicates an **IEP or 504 plan**, but neither an IEP nor a 504 plan upload was found. | Check the response and attachments. If the applicant has a plan, follow the team's secure process to obtain or locate the appropriate document. If the answer was entered incorrectly, correct it. Handle these documents according to your usual privacy procedures. |
| **Check Address** | The address is missing or incomplete, or the address could not be geocoded, so the system cannot reliably determine the catchment area. | Review the address, including street, city, state, and ZIP code, against the application and available records. Correct confirmed errors and have the address/catchment lookup run again. You may need to call the applicant to get the correct address. |

## After Reviewing an Issue

1. Correct confirmed errors in the appropriate source and make sure the updated information reaches the processing system. Changes made in Submittable will automatically resolve and apply the correct labels after a fresh extraction/mapping run; address changes also require a new address/catchment lookup.
2. [Admins only] Run the **Run validation** job again. If a check no longer finds an issue, the issue resolves automatically and its Check label is removed. A label stays if another open issue still needs it.
3. If the flagged information is correct and no change is needed, use **Mark resolved** on that specific issue in the Validation page after completing the team's review. This records an override and updates the label immediately. An override also prevents the same check from reopening on later runs, so do not use it simply to hide an issue that still needs work.
4. Do not remove these Check labels manually in Submittable; the validation process manages them and can add them back while an issue remains open.

If a label remains after a correction, check the issue message and confirm that the latest data and any needed address lookup were processed before rerunning validation.
