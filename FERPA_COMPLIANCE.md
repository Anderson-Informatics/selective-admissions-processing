# FERPA Compliance Statement — EHS Admissions Processing

This document explains what the EHS Admissions Processing application does, how
it handles education records, and the technical and procedural controls that
keep it compliant with the Family Educational Rights and Privacy Act (FERPA,
20 U.S.C. § 1232g; 34 CFR Part 99). It is intended for district review.

Items that still need attention are flagged as **[OPEN — needs resolution]**
or **[OPEN — needs expansion]** and collected in § 11.

---

## 1. What the application does

The application is a staff-only internal tool that supports the district's
selective-admissions workflow. It:

- Syncs applications and review data from **Submittable** (the system of
  record) into a MongoDB working database.
- Enriches submissions with HSPT exam results, GPA records, essay scores,
  geocoded catchment determinations, and validation checks.
- Automates stage routing, label management, score compilation, and internal
  form write-back inside Submittable.
- Lets authorized staff search submissions, run validation and background
  jobs, configure routing/scoring rules per admission cycle, send templated
  messages to applicants through Submittable, and export score/essay data.
- Exposes a read-only **Data API** (bearer-key authenticated) that returns
  applicant and application records for an authorized downstream consumer.

Applicants and parents never interact with this system directly. Parent-facing
FERPA rights (annual notification, access, amendment) are fulfilled by the
district through Submittable and the SIS, not through this tool.

## 4. Data flows

1. **Inbound:** scheduled/manual jobs pull submissions, reviews, and form
   entries from the Submittable v4 API (HTTPS, API key in env) into MongoDB.
   HSPT and GPA data arrive via staff CSV uploads. Registration sync exchanges
   student records with the district's registration API (`x-api-key`, HTTPS).
2. **Internal:** records are processed inside MongoDB — routing evaluation,
   score compilation, validation, geocoding.
3. **Outbound to vendors:**
   - **Submittable** — stage moves, label changes, internal-form score
     write-back, and applicant messages (writes back to the SOR).
   - **HERE** — the applicant's street address string only, to compute
     catchment coordinates. **[OPEN — see § 10.5]**
4. **Outbound to humans:**
   - Staff UI behind session auth.
   - File exports (score/essay XLSX) — generated on demand, stored in a
     TTL-expiring collection, downloads audit-logged.
   - Data API — bearer-key authenticated bulk read of applicant/application
     records for one authorized consumer; every call audit-logged.
5. **Deletion:** export files auto-delete via MongoDB TTL. Other record
   retention follows the district policy in § 10.6.

## 5. Access control (authentication & authorization)

- **Account model.** Staff accounts live in `users` with scrypt-hashed,
  salted passwords (`server/utils/password.ts` — no reversible storage, no
  plaintext anywhere). Password policy: ≥ 12 characters, letter + number.
- **Enrollment is invite-only.** There is no self-registration. A site admin
  generates a single-use, expiring invitation link and delivers it manually;
  the invitee sets their own password. Password resets follow the same
  pattern — a `/forgot-password` request flags the account and a site admin
  issues a manual reset link. No PII or credentials are ever emailed by the
  system.
- **Roles (least privilege / legitimate educational interest):**
  - `central_admin` (default) — full operational access to admissions data,
    exports, jobs, and configuration; *cannot* access user management.
  - `site_admin` — everything plus user management (`/admin/users` UI and
    `/api/admin/users/*` endpoints enforced server-side by `requireRole`).
- **Session security.** Sealed HTTP-only cookies (`SameSite=Lax`, `Secure` in
  production, 7-day max age) via `server/utils/auth.ts`. Sessions carry only
  `userId`, `email`, `role` — no PII.
- **Brute-force protection.** Five consecutive failed logins lock the account
  for 15 minutes; the lockout is audit-logged. Unknown and disabled accounts
  produce identical errors with timing equalization to prevent enumeration.
- **Self-protection.** A site admin cannot disable or demote their own
  account, preventing accidental lockout of all administration.
- **Bootstrap.** The first site admin is seeded from
  `NUXT_BOOTSTRAP_ADMIN_*` env vars only when the user collection is empty
  (`server/utils/seedAdmin.ts`). **[OPEN — § 10.1: clear these vars after
  first deploy.]**
- **[OPEN — needs expansion § 10.2]** Authentication is currently
  single-factor. The MSAL/Entra ID SSO path is reserved in config; when
  enabled, MFA moves to district directory controls.

## 6. Audit trail and § 99.32 disclosure records

FERPA § 99.32 requires recording each request for, and disclosure of,
education records. The `auditlogs` collection covers:

- **Disclosures:** `pii_export` (score/essay workbook downloads, with actor,
  cycle, file, row counts), `data_api_disclosure` (every Data API response —
  actor `data-api`, format, page/size), `applicant_message_sent` (templated
  messages, with subject and submission).
- **Authorization changes:** `user_invited`, `user_registered`,
  `user_updated` (role/status changes), `reset_link_created`,
  `password_reset_requested`/`_completed`, `account_locked`,
  `invite_revoked`.
- **Configuration changes (pre-existing):** routing config updates,
  stage reconciliation, score write-backs, essay stage moves — all
  actor-tagged with before/after diffs and content hashes.

**[OPEN — needs expansion § 10.7]** There is no UI or export endpoint for the
disclosure log; parent § 99.32 requests currently require a direct MongoDB
query (procedure documented in `FERPA_COMPLIANCE_FOLLOWUPS.md` § 4).

## 7. Data minimization and retention controls

- **Export TTL.** Downloadable workbooks are stored in `exportfiles` with a
  7-day MongoDB TTL index — copies of education records do not accumulate
  inside job results. (`server/utils/exportFiles.ts`)
- **Data API projection.** The API returns fixed, documented field lists —
  not raw `mappedFields` dumps — with pagination caps (≤ 100/page) and CSV
  formula-injection escaping. (`server/api/data/`)
- **Geocoding minimization.** Only the address string is sent to HERE; no
  name, DOB, or student number accompanies it.
- **Session minimization.** Cookies contain identifiers and role only.
- **[OPEN § 10.6]** Retention of submissions/jobs/audit logs across closed
  cycles is governed by district policy — the application has no automatic
  purge yet; the policy template is in `FERPA_COMPLIANCE_FOLLOWUPS.md` § 3.

## 8. Platform and transport security

- **Headers:** CSP, `X-Frame-Options: DENY`/`frame-ancestors`, `nosniff`,
  `Referrer-Policy`, `Permissions-Policy` set on all routes
  (`nuxt.config.ts` route rules). CSP permits `script-src 'unsafe-inline'`
  because Nuxt renders its SSR payload inline — tightening this is optional
  hardening, not a compliance gap.
- **Secrets:** all credentials live in `NUXT_*` env vars; `.env` is
  git-ignored; nothing secret ships to the client (`public:` config contains
  only the app URL). The Data API uses a key + separate HMAC secret with
  timing-safe comparison. Job-dispatch calls between functions require a
  shared secret header.
- **Transport:** all outbound calls (Submittable, HERE, registration API,
  inter-function dispatch) use HTTPS. MongoDB traffic uses the Atlas TLS
  connection string.
- **Dependencies:** fixed versions via `pnpm` lockfile; Renovate configured.
- **Devtools:** disabled in production builds.

## 9. Logging posture

Server-side logging contains **no student PII**. All `console.*` statements
emit job IDs, counts, stage names, and error messages only — never
`mappedFields`, names, addresses, or scores. Job failure entries reference
`submissionId` values (opaque identifiers), not names.

**[OPEN — needs resolution § 10.8]** Two residual exposures in logs:
- The submissions list accepts a `?q=` query parameter, so applicant
  name/email fragments may appear in Netlify function request URLs. Options:
  accept the residual risk (single-operator log access), move search to a
  POST body, or confirm Netlify log retention is acceptable.
- The admin-bootstrap success line logs the bootstrap admin *email* (staff
  data, low sensitivity).

## 11. Summary

The application maintains FERPA compliance through:

1. **Confined disclosure** — records are shared only with contractually
   covered processors (Submittable per district agreement; hosting under the
   contractor's FERPA-bound agreement) and one keyed Data API consumer.
2. **Least-privilege access** — invite-only accounts, scrypt-hashed
   credentials, role-based authorization, brute-force lockout, sealed
   HTTP-only sessions.
3. **Complete disclosure records** — § 99.32 audit entries on every export,
   data-API response, and applicant message, plus all authorization changes.
4. **Minimization** — fixed API projections, address-only geocoding,
   7-day-expiring export files, PII-free logging.
5. **Baseline hardening** — security headers, TLS everywhere, env-managed
   secrets, production devtools off.

The open items in § 10 are governance and hardening decisions — none are
known compliance violations, but 10.4 (Netlify ownership), 10.5 (HERE
addresses), and 10.6 (retention policy) deserve district sign-off.
