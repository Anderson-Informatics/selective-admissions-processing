EHS Admissions Automation — Jobs Specification

This document describes the processing jobs that are currently implemented and runnable. It explains what each job does, which Submittable endpoints it calls, and which MongoDB collections and documents it reads or changes.

Implementation status: metadata_sync, submission_extraction, and form_response_mapping are functional. score_compilation is visible in the Jobs UI but its handler is not implemented and currently fails when run.

1. Shared Job Lifecycle

Creation

The Jobs page sends an authenticated request to the application:

POST /api/jobs

{
  "type": "metadata_sync | submission_extraction | form_response_mapping",
  "cycleId": "selected-cycle-id",
  "payload": {}
}

The application creates a document in the jobs collection with status: "pending", the selected cycle, the authenticated user's email, and initial queued progress.

Dispatch and execution

  1. In production, the API requests the internal Netlify dispatch-jobs function after creating the job.
  2. The dispatcher leases pending jobs, respecting the configured concurrency limit.
  3. The worker claims a leased job, changes its status to running, records startedAt, and increments attempts.
  4. The registered handler executes and periodically persists progress.
  5. On success, the job becomes completed and receives its result and completedAt.
  6. On failure, the error message is stored. Expired or failed work may be retried up to the configured maximum, which defaults to three attempts.

Shared job document updates

FieldHow it is used
statuspending, waiting, running, completed, or failed.
cycleIdLimits job processing to the selected admissions cycle.
createdByEmail address of the authenticated user who queued the job.
progressCurrent phase, counts, percentage, and human-readable message.
resultJob-specific completion counts and summaries.

startedAt and completedAtRecord execution timing.

2. metadata_sync

Purpose

Downloads the organization's current Submittable projects, form definitions, labels, and team members. It stores this information in MongoDB so application configuration, review-stage configuration, field mapping, extraction, and response mapping can operate from local metadata.

Prerequisites

  • A selected admissions cycle.
  • A valid Submittable API key.
  • A configured Submittable base URL, or the default v4 API URL.

Execution flow

  1. Mark the job as fetching metadata.
  2. Fetch projects, the form list, labels, and team members concurrently.
  3. Remove duplicate objects from each response by its Submittable identifier.
  4. Fetch the complete schema for every form, with at most three schema requests running concurrently.
  5. Build MongoDB upsert operations for projects, full form schemas, labels, and team members.
  6. Write the metadata operations in batches of 1,000.
  7. Mark the job complete and save counts by metadata type.

Submittable endpoints

All requests use HTTP GET, JSON responses, and Basic authorization. The default base URL is https://submittable-api.submittable.com/v4.

EndpointPaginationPurpose
GET /projects?size=50Continues with continuationToken until absent.Retrieve projects, initial-form references, and review-stage definitions.
GET /forms?size=500Continues with continuationToken until absent.Retrieve the organization's form IDs and names.
GET /forms/{formId}One request per unique form ID; concurrency is limited to three.Retrieve each form's fields, field types, required flags, and option labels.
GET /labels?size=500Continues with continuationToken until absent.Retrieve organization labels.
GET /organizations/teamSingle request.Retrieve team member IDs, names, and email addresses.

MongoDB access

Collection/modelAccessDocuments and fields
jobs / JobRead and updateUpdates status, progress, result, error, attempts, leases, and timestamps.
metadatas / MetadataUpsertStores project, form, label, and team documents.

Metadata upsert behavior

Each object is matched by:

{
  "type": "project | form | label | team",
  "externalId": "Submittable identifier"
}

The job sets:

  • cycleId to the selected cycle.
  • name to the object's display name.
  • data to the normalized Submittable response.
  • syncedAt to the current synchronization time.

Existing matching documents are updated; missing documents are inserted. The uniqueness rule is type + externalId, not cycleId + type + externalId. Consequently, synchronizing the same Submittable object for a later cycle updates the existing metadata document and its cycleId.

Stored data by metadata type

TypeKey contents
projectProject ID, name, initial form ID, and review stages.
formForm ID, name, fields, field types, required flags, and option IDs/labels.
labelLabel ID and name.
teamUser ID, email, first name, and last name.

Progress and result

Typical phases include fetching, fetching_forms, writing, and completed. The result has this shape:

{
  "projects": 12,
  "forms": 48,
  "labels": 30,
  "team": 8
}

What this job does not do

  • It does not download form responses or submissions.
  • It does not create application or review-stage configuration records.
  • It does not create field mappings.
  • It does not delete local metadata that has disappeared from Submittable.
  • It does not update Submittable.

3. submission_extraction

Purpose

Downloads raw Submittable entries for forms that have at least one configured canonical field mapping. It stores one local FormEntry document per Submittable entry and builds or updates a consolidated Submission document for each Submittable submission.

Prerequisites

  • Metadata Sync has retrieved the relevant form schemas.
  • Submittable projects have been mapped to local applications for the selected cycle.
  • Initial forms and review-stage forms are associated with those applications.
  • At least one field on a form has a nonempty canonical field mapping.

Parent and child job design

The initial submission_extraction document is a parent job:

  1. Find distinct form IDs with nonempty field mappings for the selected cycle.
  2. Read local form metadata to obtain each form's display name.
  3. Create one submission_extraction_form child job for every mapped form.
  4. Change the parent to waiting while child jobs run.
  5. Aggregate child status and entry counts back into the parent result.

This design allows large forms to be processed independently and retried without rerunning every form.

Submittable endpoint

EndpointPaginationPurpose
GET /entries/forms/{formId}?size=500Continues with continuationToken until absent.Retrieve raw entries for one mapped form.

Each child job calls this endpoint for its assigned form. Every response page is processed before the next page is fetched, so the complete response set is not retained in memory.

MongoDB access

Collection/modelAccessPurpose
jobs / JobRead, insert, and updateReads existing children, creates per-form child jobs, and updates parent/child progress and results.
fieldmappings / FieldMappingReadFinds distinct form IDs having at least one nonempty mapping for the cycle.
metadatas / MetadataReadGets names for mapped forms.
applications / ApplicationReadBuilds a lookup from Submittable projectId to local applicationId.
reviewstages / ReviewStageReadBuilds lookups from formId + projectId to stage name and from formId + stageId to application/stage metadata.
formentries / FormEntryUpsertStores raw Submittable initial form entries.
reviews / ReviewUpsertStores raw Submittable review form entries, linked by submission ID and configured stage.
submissions / SubmissionUpsertCreates or refreshes the submission-level record and associates entry/stage IDs.

Application and stage resolution

Before downloading a form, each child reads the selected cycle's applications and review stages to build:

projectId → applicationId
formId + projectId → review stage name
formId + stageId → review stage metadata (applicationId, name, order, requiredForProgress)
applicationId + stageId → review stage name

Initial entries are matched by projectId. Review entries have no projectId, so they are matched by the unique configured formId + stageId pair for the cycle; reviews that cannot be resolved are skipped and included in the child's skippedEntries count.

Initial FormEntry upsert

Each Submittable initial entry is matched by its globally unique entryId. The job inserts or replaces the current values of:

  • cycleId, applicationId, and projectId
  • submissionId, entryId, and formId
  • formType and status
  • completedAt, createdAt, and createdBy
  • Raw fieldData

Extraction deliberately resets:

{
  "mappedData": {},
  "isMapped": false
}

This marks the raw entry as needing a new Form Response Mapping run.

Review upsert

Review entries (formType: "review") are written to the reviews collection instead of formentries. They are matched by entryId and store the parent submissionId, the review stageId, resolved application and stage metadata, reviewer/score/assignment metadata, status, timestamps, and raw fieldData. Their mappedData and isMapped flags are also reset so the Form Response Mapping job normalizes their answers.

Submission upsert

For each entry, the job also upserts a Submission document matched by submissionId. It sets the cycle, application, project, status, source timestamps, and creator. It also uses set semantics to add:

  • The entry's entryId to entryIds.
  • The configured stage name to stageNames, when one is available.

Extraction resets the submission's normalized state:

{
  "mappedFields": {},
  "isMapped": false
}

A subsequent Form Response Mapping job must rebuild those normalized fields.

Current stage refresh

After all pages of a form have been processed, the child collects the unique projectId values seen in the initial entries. For each project it calls GET /submissions?projectId=<id>&size=500 (paginated with continuationToken) and reads the current stageId from every returned submission. It then bulk-updates the matching local submissions documents with:

  • currentStageId — the current Submittable stage ID.
  • currentStageName — the configured review-stage name resolved via applicationId + stageId, if available.
  • labelIds — the label IDs currently applied to the submission, used to identify Opt-In students.

Submissions whose current stage is not a configured review stage keep only currentStageId; the dashboard groups these as Unknown stage. Submissions that have not yet had a current stage refreshed appear as Not started.

Batching and idempotency

  • Submittable returns up to 500 entries per page.
  • Each page is converted into FormEntry, Review, and Submission bulk upserts.
  • Re-extracting an existing entryId or submissionId updates the existing document rather than creating a duplicate.
  • Existing entryIds and stageNames are deduplicated with set semantics.

Progress and result

Each child reports pages and cumulative saved/skipped counts. A child result has this shape:

{
  "formId": "Submittable form ID",
  "pages": 12,
  "entries": 5731,
  "skippedEntries": 4,
  "submissionsStaged": 5731
}

The parent result summarizes all child jobs:

{
  "forms": [
    {
      "formId": "...",
      "formName": "Initial Application",
      "childJobId": "...",
      "status": "completed",
      "entries": 5731
    }
  ],
  "entries": 5731
}

What this job does not do

  • It does not extract forms that have no configured canonical mappings.
  • It does not map raw field values to canonical field names.
  • It does not validate applicants, calculate scores, or route submissions.
  • It does not delete local entries that were deleted or removed in Submittable.
  • It does not write anything back to Submittable.

4. form_response_mapping

Purpose

Transforms previously extracted raw FormEntry and Review data into normalized canonical fields such as FirstName, LastName, DOB, and StudentNumber. It writes normalized values onto each FormEntry and Review, and combines all applicable initial entries into one normalized record on each Submission.

Existing FormEntry.fieldData + Review.fieldData
          +
Configured FieldMapping documents
          +
Cached Submittable form schemas
          ↓
FormEntry.mappedData + Review.mappedData
          ↓
Submission.mappedFields (from FormEntry only)

Prerequisites

  • Submission Extraction has populated FormEntry and Submission documents.
  • Forms have nonempty canonical field mappings for the selected cycle.
  • Mapped forms are associated with configured applications or review stages.
  • Metadata Sync has normally cached the relevant form schemas.

Execution flow

  1. Find all mapped form IDs for the selected cycle.
  2. Read applications and review stages to determine which applications contain those mapped forms.
  3. Load all nonempty field mappings for the mapped forms.
  4. Load cached form schemas and build option ID-to-label lookups.
  5. Fetch a form schema from Submittable only when it is missing locally.
  6. Count eligible FormEntry documents.
  7. Stream entries from oldest to newest, map every configured field, and update entries in batches of 500.
  8. Combine mapped values by submissionId.
  9. Update Submission documents in batches of 500.
  10. Store completion counts in the job result.

Submittable endpoints

In the normal case this job makes no Submittable request. It operates on raw entries and form schemas already stored in MongoDB.
EndpointWhen calledPurpose
GET /forms/{formId}Only when a mapped form has no locally cached schema containing fields.Retrieve field definitions and option labels needed for normalization.

This job does not call GET /entries/forms/{formId}; raw entries must already have been downloaded by Submission Extraction.

MongoDB access

Collection/modelAccessPurpose
jobs / JobRead and updateUpdates lifecycle, progress, result, errors, attempts, and timestamps.
fieldmappings / FieldMappingReadFinds mapped forms and resolves formId + fieldId to a canonical field name.
applications / ApplicationReadIncludes applications whose initial forms are mapped.
reviewstages / ReviewStageReadIncludes applications having mapped review-stage forms.
metadatas / MetadataReadLoads cached form fields and option labels.
formentries / FormEntryRead and updateReads raw fieldData; writes mappedData and isMapped.
reviews / ReviewRead and updateReads raw review fieldData; writes mappedData and isMapped.
submissions / SubmissionUpdateWrites combined mappedFields and isMapped from initial FormEntry data.

Documents selected

The job processes FormEntry documents matching:

{
  "cycleId": "selected cycle",
  "formId": { "$in": ["mapped form IDs"] },
  "applicationId": { "$in": ["applications with mapped forms"] }
}

Entries are streamed in ascending createdAt and _id order. MongoDB may use disk for the sort when necessary, and the FormEntry schema defines an index on cycleId + createdAt + _id.

Field conversion rules

Ordinary fields

An ordinary field uses its value. For example, a mapping from field-123 to FirstName converts:

{
  "formFieldId": "field-123",
  "fieldType": "text",
  "value": "Jordan"
}

into

{
  "FirstName": "Jordan"
}

Name fields

Name components are mapped independently using synthetic mapping IDs:

formFieldId:firstName
formFieldId:lastName

Address fields

Address components are mapped independently:

  • address1
  • address2
  • city
  • region
  • postalCode
  • country

Select and checkbox fields

Submittable option IDs are replaced with their human-readable form-schema labels. Multiple selections are joined with ; .

File fields

File objects are reduced to file names. Multiple files are joined with ; .

FormEntry updates

For each eligible FormEntry, the job sets:

{
  "mappedData": {
    "FirstName": "Jordan",
    "LastName": "Smith",
    "DOB": "2012-05-14"
  },
  "isMapped": true
}

The raw fieldData is not changed. Entry updates are accumulated and written in batches of 500.

Submission updates and precedence

Mapped entry values are grouped by submissionId. Initial-form and review-form values are combined into a single mappedFields object.

Because entries are processed oldest to newest, a later entry overwrites an earlier value when both map to the same canonical name. The final operation sets the complete reconstructed object:

{
  "$set": {
    "mappedFields": { "...": "combined normalized values" },
    "isMapped": true
  }
}

The job therefore replaces the previous mappedFields object with values rebuilt from all eligible entries in the current run.

Progress and result

Typical phases are loading, mapping_entries, writing_submissions, and completed. Entry mapping accounts for the first 90 percent of progress; submission writes account for the final 10 percent.

{
  "formEntries": 15234,
  "reviews": 3892,
  "submissions": 5210,
  "applicationsWithMappings": 8
}

What this job does not do

  • It does not download new entries or submissions from Submittable.
  • It does not create FormEntry or Submission documents.
  • It does not change raw fieldData.
  • It does not modify field mappings, applications, review stages, or cached metadata.
  • A fallback schema fetched from Submittable is used in memory and is not persisted by this job.
  • It does not currently execute the optional FieldMapping transform value.
  • It does not validate data, calculate scores, route submissions, or update Submittable.

5. dpscd_gpa_import

Purpose

Imports DPSCD cumulative GPA records delivered to the API as a JSON body. The job matches each record to a local submission in the cycle and upserts the dpscd subdocument on the applicant's GpaRecord.

Prerequisites

  • A selected admissions cycle with extracted submissions.
  • A staged GpaUpload document created by POST /api/gpa/dpscd holding the raw records array.

Trigger and payload

This job is not started from the generic Jobs page. The endpoint authenticates the caller, validates and stores the payload, then creates the job:

POST /api/gpa/dpscd

{
  "cycleId": "selected-cycle-id",
  "records": [ { "submissionId": "...", "submissionIdInt": "...", "STUDENT_NUMBER": 21165451.0, "Quarters Available": 11.0, "gpa_cumulative": 3.0, ... } ]
}

A bare top-level array of records is also accepted. Strict JSON is parsed first; if that fails the body is normalized from Python-style repr output (single quotes, None/True/False/nan) before parsing. The caller polls GET /api/gpa/dpscd/{uploadId} for status.

Execution flow

  1. Load the staged GpaUpload referenced by the job payload.
  2. Normalize each record's keys and coerce integer-semantic floats (STUDENT_NUMBER, submissionIdInt, Quarters Available, Latest_GRADE_LEVEL, Middle School Number, Accepting High School Number) to integers; gpa_cumulative remains a decimal.
  3. Match each record to a submission in the cycle by submissionId, then submissionIdInt, then StudentNumber.
  4. Validate values; out-of-range or mismatched fields become warnings, unmatched records become errors, neither is fatal.
  5. Bulk-upsert GpaRecord documents keyed (cycleId, submissionId), setting only the dpscd subdocument plus provenance (importJobId, importedAt).
  6. Mark the staged upload completed or failed and store the result summary.

MongoDB access

Collection/modelAccessDocuments and fields
gpauploads / GpaUploadRead and updateStaged records, status, result, error.
submissions / SubmissionReadMatch keys (submissionId, submissionIdInt, mappedFields.StudentNumber).
gparecords / GpaRecordUpsertSets dpscd subdocument and provenance.
jobs / JobRead and updateStatus, progress, result, error.

Progress and result

Phases include normalizing, matching, writing, and completed. The result has this shape:

{
  "processed": 1000,
  "matched": 380,
  "updated": 380,
  "unmatched": 620,
  "warnings": [ "..." ],
  "errors": [ "..." ]
}

What this job does not do

  • It does not fetch data from Submittable or DPSCD; the payload must be posted to the API first.
  • It does not write scores or select the effective GPA — that happens in score compilation.
  • It does not modify submissions or the optIn subdocument on existing records.
  • Unmatched records (other years, other projects) are reported but not imported.

6. optin_gpa_preview

Purpose

Parses uploaded Opt-In XLSX files (one per out-of-district school), matches each row to a submission by submissionIdInt, and reports per-row status so staff can review the import before anything is written.

Prerequisites

  • A selected admissions cycle with extracted submissions.
  • A staged GpaUpload (source: 'opt_in', status: 'previewing') created by the GPA page upload.

Trigger and payload

POST /api/gpa/optin/uploads   (multipart: cycleId + one or more .xlsx files)

Execution flow

  1. Load the staged upload and decode each base64 file.
  2. Parse each workbook: extract the school name from the SCHOOL NAME: banner row, locate the header row, and read the student rows.
  3. Ensure submissions carry labelIds; backfill them from Submittable for the cycle's projects when missing.
  4. Resolve the Opt-In label id from the synced label metadata (case-insensitive opt-in/opt in/optin match).
  5. Match each row to a submission by submissionIdInt and classify it: matched, missing_optin_label, unmatched, invalid_gpa, or not_enrolled.
  6. Count Opt-In-labeled submissions absent from all files (optInMissingFromFile).
  7. Store the preview on the upload document and set its status to ready.

MongoDB access

Collection/modelAccessDocuments and fields
gpauploads / GpaUploadRead and updateStaged files, status, preview, error.
submissions / SubmissionRead and updateMatch keys and labelIds backfill.
metadatas / MetadataReadLabel catalog used to resolve the Opt-In label id.
jobs / JobRead and updateStatus, progress, result, error.

Submittable endpoints

EndpointPurpose
GET /submissions?projectId=…&size=500Backfill labelIds for the cycle's submissions when they are missing.

Progress and result

What this job does not do

  • It does not write any GPA data; it only stages and describes the import.
  • It does not modify Opt-In labels in Submittable.

7. optin_gpa_commit

Purpose

Applies a confirmed Opt-In upload: upserts the optIn subdocument on GpaRecord for each matched file row. Only submissions whose submissionIdInt appears in the uploaded files are modified.

Prerequisites

  • A staged GpaUpload in confirming status, transitioned by POST /api/gpa/optin/uploads/{id}/confirm.

Execution flow

  1. Load the staged upload and re-parse each XLSX file.
  2. Match rows to submissions by submissionIdInt; skip unmatched rows.
  3. Normalize enrollment answers (Yes/No, case-insensitive) and GPA values.
  4. Bulk-upsert GpaRecord.optIn for matched rows, flagging rows whose submission lacks the Opt-In label as warnings (they are still imported).
  5. Mark the upload completed, clear stored file payloads, and save the result summary.

Progress and result

{
  "processed": 87,
  "updated": 80,
  "skippedUnmatched": 3,
  "missingOptInLabel": 4,
  "warnings": [ "..." ],
  "errors": []
}

What this job does not do

  • It does not touch submissions that are not present in the uploaded files.
  • It does not select the effective GPA or write scores — that happens in score compilation.
  • It does not modify the dpscd subdocument on existing records.

8. Recommended Pipeline Order

  1. Metadata Sync — download current Submittable projects, forms, labels, and team members.
  2. Application configuration — map Submittable projects and review stages to the selected cycle.
  3. Field mapping — assign canonical names to fields on initial and review forms.
  4. Submission Extraction — download raw entries and build local FormEntry and Submission documents.
  5. Form Response Mapping — normalize raw values and build each submission's consolidated mapped fields.
  6. Validation — run data-quality rules and create/resolve validation issues.
  7. Catchment lookup — geocode addresses and determine catchment zones.
  8. GPA data ingestion — import the DPSCD GPA payload via the API endpoint and stage/confirm Opt-In XLSX uploads from the GPA page.
  9. Scoring and routing — planned but not currently implemented.

Submission Extraction resets mapping state, so Form Response Mapping should be rerun after every extraction that updates entries for the cycle.
