# Project Notes

## Tech Stack
- Nuxt 4 (`nuxt` ^4.5.2) with Nuxt UI v4 (`@nuxt/ui` ^4.11.0) and Tailwind CSS v4.
- Netlify Nitro server preset is used by default when `npm run build` runs on Netlify (or add `preset: 'netlify'` to `nuxt.config.ts`).
- MongoDB via Mongoose (`mongoose` ^9.9.4).
- pnpm is the configured package manager (`packageManager` in `package.json`).

## Commands
- `pnpm install` — install dependencies.
- `pnpm dev` — start the development server at `http://localhost:3000`.
- `pnpm build` — build for production.
- `pnpm preview` — preview the production build locally.
- `pnpm lint` — run ESLint.
- `pnpm typecheck` — run Vue/Nuxt type checking.
- `pnpm test` — run Vitest unit and mocked route/workflow tests; these do not use live MongoDB or Submittable.
- Verification baseline on 2026-11-03: tests, lint, typecheck, and the default local production build pass. The build may emit non-fatal font-network/tooling warnings. Local builds use the Node server preset unless a deployment preset is selected; verify Netlify background functions separately.
- CI runs lint, typecheck, tests, and a production build on pushes and pull requests.
- Verify Netlify bundling locally with `NITRO_PRESET=netlify pnpm build`. Keep `nitro.externals.inline: ['xlsx']`: without the package-name matcher, Nitro can emit absolute build-machine imports for `xlsx/dist/cpexcel.js`. The helper must be bundled in `.netlify/functions-internal/server/chunks/nitro/nitro.mjs`, not imported from the source `node_modules`.

## Environment Variables
Copy `.env.example` to `.env` and fill in values. Runtime config keys must be prefixed with `NUXT_` to be available in Nitro server routes. Public keys need to be prefixed with `NUXT_PUBLIC_` for client access.

## Code Conventions
- Use TypeScript. Keep `.vue` components in `app/components/` and pages in `app/pages/`.
- Server API routes live in `server/api/` and server utils in `server/utils/`.
- Use Nuxt UI components (`UButton`, `UInput`, `UTable`, etc.) for UI.
- Avoid adding secrets or `.env` files to git (`.env` and `.env.*` are ignored, except `.env.example`).

## Domain Notes
- Admission rounds live on `Application.rounds` (not Cycle). `resolveSubmissionRound` is fed per-application rounds in `routingRun.ts` and `reviewCompletionRefresh.ts`. A boot-time migration (`server/utils/migrateRounds.ts`, run from `server/plugins/db.ts`) copies legacy `cycle.rounds` data onto applications and unsets it.
- Submittable re-issues `reviewStageId` when a stage is modified. `metadata_sync` runs `applyStageReconcile` (`server/utils/stageReconcile.ts`) which remaps unambiguous old→new stageIds in place across ReviewStage, Review, Submission.currentStageId, `routing`/`routingDraft` configs, and dashboard metrics; ambiguous/orphan cases land in the job result. Routing configs must never be replaced — stageId references are rewritten via `rewriteReferencedStageIds` in `routingConfig.ts`. `routingHistory` is intentionally not rewritten.
- `routing` is the published config; `routingDraft` is the working copy written by the stage PATCH endpoint and promoted by `routing-publish`.
- Withdrawn submissions use system-level handling, not routing config rules: `Submission.status` matching `/^withdrawn$/i` makes `Withdrawn Application` the only required ledger stage, routes only to that stage (even when its stage routing is disabled), suppresses configured routing side effects, and removes managed stage `statusLabels` plus `scoring.gpaStatusLabels` during refresh/routing cleanup. Extraction, mapping, review history, registration deletion, validation-label cleanup, submission detail/audit views, and the duplicate-student-number audit still include withdrawn records; active reporting, HSPT matching/linking, GPA/score compilation, and internal-form write-back exclude them.
- Daily job chains are configured at `/jobs/scheduler`. `tickJobSchedules` runs from both Netlify dispatch and the local worker, snapshots the active cycle per occurrence, and serializes scheduled runs per cycle using `ScheduleCycle.runId`. Manual jobs are not globally excluded.
- Scheduled automatic refresh jobs start in `waiting` with `dependencyOf`; the scheduler releases them only after the root job settles. Preserve `scheduleRunId`, `scheduleStep`, `executionKey`, and `workerSettled` semantics when changing job lifecycle logic. Failed/interrupted scheduled routing or essay actions hold the cycle for explicit operator review rather than replaying automatically.
- `score_compilation` runs a per-application recipe configured on `Application.scoring` (`server/utils/scoreCompilation.ts`) for non-withdrawn submissions and deletes stale `ScoreRecord`s for withdrawn submissions. It writes `ScoreRecord` docs with two totals: `totalAppScore` (Exam + GPA_Score + Essay + DPSCD bonus) and `totalMarygroveScore` (adds the Marygrove catchment bonus) — placement uses the MG total only for Marygrove seats. `requireComplete` gates totals on HSPT+GPA+essay readiness (legacy behavior). `payload.dryRun` compiles without persisting, deleting stale records, or writing back.
- GPA math lives in `server/utils/gpaScoring.ts`: `GPA_Score = bandedTable(gpa) * multiplier + bonus`. The 30-point table is config (`scoring.gpaTable`); the bonus (`scoring.gpaBonusPoints`, default 5) applies when the submission has the "GPA Bonus Eligible" label. Multiplier cascade: 1 for recording/Opt-In/DPSCD≥6 quarters, else Partial-GPA `Semesters` option map, else DPSCD `Quarters Available` (5→0.8, 4→0.6, 2–3→0.4, 1→0.2). `reviewCompletionRefresh` stamps `gpaMultiplier/gpaBonusEligible/gpaBonus/gpaScore` on `GpaRecord` alongside `resolvedCumulativeGpa`/`resolvedSource`, but deletes and does not recreate `GpaRecord`s for withdrawn submissions.
- GPA status labels are application-level (`scoring.gpaStatusLabels`), not stage `statusLabels`, because GPA resolution spans GPA Recording, DPSCD, Opt-In, and Partial GPA sources. `server/utils/gpaStatusLabels.ts` synchronizes persisted `Submission.gpaStatus` after non-dry-run `refresh_review_completion`; `gpa_status_label_sync` is the standalone dry-run-capable repair job. Each configured status must map to a distinct Submittable label.
- The `/api/gpa` review table is submission-based (not GpaRecord-based) so every applicant appears. Its response also includes a cycle-wide `duplicateStudentNumbers` report grouped by nonblank `mappedFields.StudentNumber`; the UI displays it only when the final-source filter is DPSCD/PowerSchool. `resolveGpa` precedence is GPA Recording → DPSCD/PowerSchool → Opt-In → Partial GPA. Canonical `gpaStatus` values are `Complete`, `Partial`, `DPSCD Partial`, `Opt-In Partial`, and `Incomplete`; `OOD Partial` is legacy and canonicalized/migrated by `migrateOptInPartialStatus.ts`.
- Internal form write-back (`server/utils/internalFormSync.ts`) uses documented v4 endpoints: `GET /entries/submissions/{id}` → `PUT /entries/{entryId}` with full `fieldData` (diff-only — skips unchanged), or `POST /entries/internal` when no internal entry exists. Canonical score field → `formFieldId` mapping lives in `scoring.internalForm.fields`; `PATCH /entries` does NOT support `formType:'internal'`. Legacy fieldId lists are seeded in `server/config/seeds/scoring/`. `Application.placementPathway` ('score'|'decision') is set aside for the future placement algorithm.
- Auth is DB-backed (`server/models/User.ts`): scrypt-hashed passwords (`server/utils/password.ts`), roles `site_admin`/`central_admin`. Users are created only via site-admin invitation links (`AuthToken` model, `/accept-invite`); password resets work the same way (`/reset-password`, links generated by a site admin after a `/forgot-password` request flags the account — nothing is emailed automatically). `requireAuth` returns `{ userId, email, role }`; admin routes use `requireRole(event, 'site_admin')`. The first site admin is provisioned manually in MongoDB (there is no bootstrap seeder). Accounts lock for 15 minutes after 5 failed logins.
- FERPA disclosure logging (`server/utils/disclosureAudit.ts`) writes `pii_export`/`data_api_disclosure`/`applicant_message_sent` entries to AuditLog on exports, the data API, and applicant messaging. Essay export files are stored in the `ExportFile` collection with a 7-day TTL (`server/utils/exportFiles.ts`), not inside job results.
- DPSCD GPA JSON imports use `STUDENT_NUMBER` plus canonical `StudentName`, `DOB`, `SchoolNumber`/`SchoolName`, `latestGradeLevel`, `minimumEntryDate`, `latestExitDate`, and `_r1`/`_all` snapshot fields. Optional `submissionId`/`submissionIdInt` remain higher-priority match fields; `Middle School Number` is a legacy alias for `SchoolNumber`. `selectDpscdSnapshot` uses each submission's application rounds (`order: 1` → `r1`, subsequent rounds → `all`), with no fallback for unresolved rounds/missing snapshots. Student-number imports update all matching non-withdrawn submissions in the cycle and clear stale `GpaRecord`s for withdrawn submissions. DPSCD data below six quarters requires a usable completed GPA Recording or Partial GPA review for scoring; uncalculated GPA scores are null. `POST /api/gpa/dpscd?dryRun=true` stages a preview job (first 200 matched submissions) without GPA writes or completion refresh. Do not modify routing configurations for this ingestion flow.
- DPSCD import/upload polling accepts a session or `Authorization: Bearer <NUXT_DATA_KEY>` via `requireDpscdAccess` (also requires `NUXT_DATA_SECRET`). A supplied Authorization header must validate; invalid keys never fall back to sessions. Key-created uploads/jobs use `service:dpscd-data-api`; key-based `/api/jobs/:id` polling is limited to that actor's `dpscd_gpa_import` jobs and disallows routing batches. Key-based result reads are disclosure-audited.
- Vitest cannot resolve the `~~` alias: every `~~/…` import in tested modules must be mocked, or use relative imports in files under test.
